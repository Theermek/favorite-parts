# Поиск автозапчастей и аналогов (Favorit Parts API)

Одностраничное приложение для двухэтапного подбора запчастей:

1. ввод артикула → список производителей (брендов);
2. выбор бренда → таблица детали и её аналогов с предложениями по складам.

## Запуск

```bash
npm install
cp .env.example .env     # вписать ключ покупателя в FAVORIT_API_KEY
npm run dev              # http://localhost:5173
```

Ключ покупателя нам не выдавали, поэтому в разработке используется демо-ключ из
публичной документации поставщика
(https://lk.favorit-parts.ru/static/wsprice.pdf) — на момент написания он
работает на боевом эндпоинте.

## Стек

React + Vite (JavaScript), Redux Toolkit + react-redux, Bootstrap (только CSS),
нативный `fetch`. Зависимостей ровно пять: `react`, `react-dom`,
`@reduxjs/toolkit`, `react-redux`, `bootstrap`. Без TypeScript, роутинга,
RTK Query, axios и UI-китов.

## Структура

```
vite.config.js             dev-прокси: CORS + подстановка ключа
api/index.js               serverless-прокси для прода (Vercel)
src/api/favoritApi.js      запрос, разбор ответа, маппинг в плоские строки
src/store/store.js
src/store/searchSlice.js   fetchBrands, fetchOffers (createAsyncThunk)
src/components/            SearchForm, BrandList, OffersTable, Loader, ErrorAlert
```

## Ключ и CORS

Запросы идут на относительный `/api`, а прокси из `vite.config.js` переписывает
их на `http://api.favorit-parts.ru/hs/hsprice/` и дописывает ключ. Это решает CORS
и оставляет ключ на стороне сервера разработки.

Ключ лежит в `.env` (в `.gitignore`), в репозитории — только `.env.example`.
Переменная называется `FAVORIT_API_KEY` **без префикса `VITE_`**: любую `VITE_*`
переменную Vite встраивает в клиентский бандл, что свело бы защиту на нет.
`vite.config.js` читает её через `loadEnv(mode, cwd, '')` — третий аргумент `''`
разрешает переменные без префикса. Проверено: после `npm run build` ни ключа, ни
имени переменной в `dist/` нет.

Dev-прокси живёт только в `vite dev` — при `npm run build` его не существует.
Поэтому для развёрнутой версии ту же роль играет serverless-функция
`api/index.js` (см. «Публикация»): ключ и там остаётся на сервере.

## Публикация

Развёрнутая версия: **<!-- URL -->** (ссылку добавим после первого деплоя).

Схема одинаковая в обоих окружениях — клиент всегда зовёт относительный `/api`,
а ключ подставляется на сервере:

| Окружение | Кто подставляет ключ | Откуда берёт |
|---|---|---|
| Локально (`npm run dev`) | dev-прокси в `vite.config.js` | `.env`, переменная `FAVORIT_API_KEY` |
| Продакшен (Vercel) | serverless-функция `api/index.js` | Environment Variable `FAVORIT_API_KEY` |

Благодаря совпадению пути `/api` код приложения в обоих случаях один и тот же —
ни одной ветки «если прод» в `src/`.

Как развернуть свою копию:

1. На vercel.com войти через GitHub и импортировать этот репозиторий.
2. В Settings → Environment Variables добавить `FAVORIT_API_KEY` с ключом покупателя.
3. Deploy. Vite-пресет и каталог `dist` определяются автоматически, конфиг не нужен.

Функция отдаёт тело ответа поставщика как есть и пробрасывает его HTTP-статус;
свои ошибки она возвращает в том же виде `{ "error": "..." }`, поэтому они
попадают в тот же разбор и тот же alert, что и ошибки API.

## Принятые решения

- **Цена — только из `warehouses[].price`**, `goods.price` по документации устарел.
  Остаток в строке — тоже складской (`warehouses[].stock`), а не `goods.count`:
  `count` суммирует все склады и при разбивке по складам соврал бы.
- **Разбор ответа идёт в порядке «тело → статус».** Ошибки приходят и с HTTP 200,
  и с HTTP 403 (`{"error":"Empty key!"}`), поэтому проверка `response.ok` первой
  съела бы понятный текст ошибки.
- **`encodeURIComponent` для `number` и `brand` обязателен.** У бренда
  `Meat & Doria` сырой `&` рвёт query, и API молча отвечает пустышкой «не
  найдено» вместо ошибки. Слэш в `NGK/NTK` кодируется в `%2F` и доходит корректно.
- **`analogues` лежит внутри самого товара** (`goods[0].analogues`) и возвращается
  только вместе с параметром `brand`; у самих аналогов вложенных аналогов нет.
- **Пагинация в таблице.** Ответ с аналогами бывает огромным: запрос
  `81022E` / `Meat & Doria` вернул 3.4 МБ и 3860 товаров, то есть 15 000+ строк
  после разбивки «товар × склад». Такая таблица подвешивает вкладку, поэтому
  рендерим по 100 строк с кнопкой «Показать ещё» и подписью «Показано N из M».
- **Гонки запросов** отсекаются штатным механизмом RTK: `requestId` из
  `action.meta` сохраняется в `pending` и сверяется в `fulfilled`/`rejected`.
  Проверено на втором этапе: если кликнуть медленный бренд, а следом быстрый,
  пришедший позже «медленный» ответ таблицу не перезаписывает.
- **Поиск только по кнопке или Enter**, без поиска на каждый символ — у API есть
  квота на запросы (`Request quota exceeded!`). Пока запрос идёт, кнопка
  отключена, поэтому повторная отправка той же формы невозможна.
- Поле `warehouseShipping` приходит в ответе, но в документации не описано — не
  используем.

## Обработанные edge cases

| Случай | Поведение |
|---|---|
| Деталь не найдена | API отдаёт HTTP 200 и один элемент-пустышку с `goodsID` из нулей — отбрасываем его и показываем «Ничего не найдено» |
| Ошибка API | `{"error":"..."}` (с 200 или 403) — текст ошибки в Bootstrap alert |
| Нет в наличии | `count: 0`, `warehouses: []` — строка с пометкой «нет в наличии», без цены |
| Сбой сети | `fetch` падает — показываем «Не удалось связаться с сервисом…» |
| Бренд со спецсимволами | `NGK/NTK`, `Meat & Doria` — через `encodeURIComponent` |
| Очень большой ответ | 15 000+ строк — порциями по 100 |
| Устаревший ответ | игнорируется по `requestId` |
| Новый поиск | сбрасывает выбранный бренд и таблицу |
